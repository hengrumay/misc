RWE ADS Automation — architecture & where agents fit

Turning study protocols into analysis-ready datasets on Databricks · as-built v1.5 · draft for internal review before any external use

AS-BUILT · SYNTHETIC PoC
As-built status. The recommended architecture below is implemented and validated end-to-end for all three PoCs (poc_low / poc_med / poc_high). The previously-open piece — PDF/DOCX extraction — is done: ai_parse_document → ai_extract turns protocol files into the structured spec that drives the build. Markdown parsing remains only as a narrative-only fallback. The As-built column in §2 maps each recommended step to the live component.

In plain English. Turn a study protocol (a document describing an epidemiology study) into an analysis-ready dataset (ADS) on governed data by assembling pre-approved SQL building blocks (not free-form model-generated SQL), validating each step, and requiring a recorded human approval before results are used. Most of the workflow is a predictable, governed pipeline; an AI "agent" is genuinely valuable in one place — letting an analyst ask questions of the finished dataset — and that is optional.

1 · The big picture

Study protocol (PDF/DOCX) → Extract fields → Structured spec → Build ADS SQL → Validate + review → Approved ADS + audit trail

A governed, predictable pipeline. SQL comes from the approved knowledge base; every step is validated; a human approves before use.

3 · Where an agent genuinely adds value

Keep it a governed pipeline (CORE)

  • Document extraction → structured spec: AI Functions in a job — ✅ built
  • ADS SQL from the approved KB, validated before use — ✅ built
  • Orchestration: native Workflows/Jobs + pipelines (serverless) — ✅ built
  • Human review + approval; reproducibility + audit — ✅ built

Predictable, governed, easy to audit — the right default for a regulated workflow.

Add an agent only where it earns its place (OPTIONAL)

  • Genie for analyst Q&A over the approved ADS tables — the clearest fit. optional — config placeholder (point a Genie space at the approved ads_output post-deploy)
  • Multi-agent orchestration — only if the workflow becomes genuinely dynamic (branching). A native Workflow already covers a fixed pipeline. Not built (by design).

Reserve "agent" for genuinely dynamic reasoning — not a fixed pipeline.

4 · Data posture & one honest divergence

  • Data posture: synthetic / de-identified only — deterministic synthetic RWD (Faker, fixed seed) + synthetic protocol fixtures; no PHI. Real redacted protocols are fine when cleared to share.
  • AI Gateway routing (note): the extraction AI Functions are native, in-platform calls — external-egress denial is inherently satisfied, but they don't route through the named ads-ai-gateway endpoint, and PHI masking isn't applied to extraction input unless ai_mask runs first (today it relies on synthetic/redacted inputs). Strict gateway routing is a documented follow-on, not a blocker for synthetic data.
  • Eval gate (what blocks e-sign): the hard gate is Stage-1 deterministic validators (eval_ok) — a spec that fails them cannot be e-signed. Stage-3 model judges (via gateway_call) are advisory: they set review priority + flags only, never eval_ok, and silently degrade to Stage-1/2 when no judge endpoint or source text is available. It is not a model-gated eval.
  • Auto-e-sign (demo default): the shipped demo config sets allow_auto_esign: true, which auto-signs eval-passing specs under a SYSTEM actor (a non-human signature, explicitly not a 21 CFR Part 11 human e-signature), bypassing the human analyst e-sign. The human e-sign path is real code but off by default — set allow_auto_esign: false for any regulated use.
  • poc_high scope: lab-value (LOINC) covariates await a der_baseline_lab_value snippet through the KB approval path; poc_high is built from approved comorbidity/exposure/outcome snippets.
  • Enrollment window: defaults to 90 days (synthetic enrollment spans are short); the outcome follow-up window stays faithful to each protocol (365/730 days).

5 · Reproduce on a Windows laptop (UI-first)

Runs entirely against the Databricks web UI plus a few PowerShell commands. Everything is serverless — no local Spark, no cluster to manage.

One-time setup (Windows)

  • Install (PowerShell, one line each): winget install Databricks.DatabricksCLI · winget install Git.Git · winget install Python.Python.3.11 · winget install OpenJS.NodeJS.LTS. Close & reopen PowerShell after.
  • Optional GUIs: GitHub Desktop (clone the repo by clicking) and VS Code (edit demo.config.yaml).
  • You need access to your Databricks workspace <your-workspace>.cloud.databricks.com with permission to run jobs, pipelines, and Apps.

Steps

  1. Get the code. GitHub Desktop → Clone repository → URL → <your-org>/<your-repo> (or PowerShell: git clone https://github.com/<your-org>/<your-repo>.git).
  2. Sign in to Databricks. In PowerShell, in the repo folder: databricks auth login --profile <your-profile> (or --host https://<your-workspace>.cloud.databricks.com) — a browser window opens; approve. (This is the only auth step; it uses your normal SSO login.)
  3. Deploy the bundle. databricks bundle deploy -t dev. This uploads the code and creates all jobs + the pipeline + the app in the workspace.
  4. Seed sample protocols & run the pipeline — from the UI. In the Databricks web UI open Workflows and run these jobs in order (click Run now, wait for green): Wave 0 Foundation → Wave 1 Synth+Bronze+Protocol → Wave 3 ADS build + eval + review → Wave 5 Audit+Serving. (Wave 1 also parses the sample protocol PDFs/DOCX; Wave 3 approves them and builds all three ADS.)
  5. Open the app. Databricks web UI → Compute → Apps → -rwe-ads-app → open the URL. You're signed in via SSO.
  6. Drive the flow in the app. Protocols page → Choose File to upload a PDF/DOCX → Run extraction → select the study to see the extracted coded spec → Approve & e-sign → Build ADS.
  7. See results & audit. Served ADS shows the cohorts (source pill = Lakebase); Review & Sign-off holds pending builds for e-sign; Audit shows the hash-chained GxP log + reproducibility manifests.
  8. (Optional) Ask questions with Genie. The bundle ships a Genie config placeholder — no space is provisioned. To enable analyst Q&A, create a Genie space in the Databricks UI pointed at the approved ads_output, then ask e.g. "How many patients are in each study cohort, and what is the outcome rate?"

Bringing your own protocols later: just drop the PDF/DOCX into the Unity Catalog volume ads_raw.protocols (Catalog UI → Volumes → Upload) and re-run the extraction step — no code change.
